# PetDiaryのNotionを維持する

開発開始時に今の目標と次にやることが分かり、必要な仕様と判断理由へ辿れる状態を保つ。管理項目を埋めることや、ページを別DBへ移すことを作業の目的にしない。

## 対象と許可

- 「整理して」「保存して」「更新して」という依頼は、その対象範囲での通常の整理と、ユーザーが明示した決定の反映を許可する。既存ページの更新、必要なタスクや資料の作成、関係の整理について、差分ごとの再承認を求めない。
- 分析、相談、レビュー、変更案の提示だけの依頼では書き込まない。ユーザーが草案のみを求めた場合も適用しない。
- 結果を左右する未決定事項、削除、依頼外への拡張、対象範囲が不明な変更だけ確認する。未決定事項は既存のタスクやメモに論点として残せるが、採用済みとして確定しない。
- このスキルを読むこと自体は、Notionの全面移行やプロダクションコードの編集の許可にならない。対象に必要な範囲だけ扱う。

## 既存6DBと参照先

DBのURLとページの同一性を維持する。タスクとメモの既存DBを使う。旧「受信箱・検討」は「メモ」として扱い、同じ用途のDBを新設しない。

| ページ・DB | 用途 | URL |
| --- | --- | --- |
| PetDiaryトップ | 開発を始めるページ | https://app.notion.com/p/3d7e571d85858158b58df07140cc9dd7 |
| 資料 | 要件・仕様・判断記録・参考メモ | https://app.notion.com/p/404e571d8585818fb649deb219cc8a7a |
| マイルストーン | 到達点と概算進捗 | https://app.notion.com/p/b68b6adbbb274fd2bc7e4465a8d59bd5 |
| タスク | 検討から実装・テストまでの作業 | https://app.notion.com/p/df84f0b8db804a35bc5c4fd40b1842d3 |
| メモ | 未整理の入力、参考情報、保留した論点 | https://app.notion.com/p/011e373b66ff42a9a52b6025c873dbaa |
| 要件 | 利用者として実現したいこと | https://app.notion.com/p/646edae384e449059ac196e570950019 |
| 仕様 | 採用した振る舞いと構造 | https://app.notion.com/p/b6d6865704894d738ed5efd4cd135d4f |
| 判断記録 | 採用した方針とその理由 | https://app.notion.com/p/c21c174a0c70431490ede31e9b8188db |

要件・仕様・判断記録は独立したDBを保ち、共通の「資料」ページから参照する。「資料」は7つ目の管理DBや、分類Propertyで3DBを置き換える単一DBではない。ページ内の小さな補助表を主要管理DBへ増やさない。

アーカイブ内の移行前DB・データはロールバック用に残す。ユーザーの個別承認なしに削除、Trash移動、アーカイブ内のRelation削除をしない。旧DBが見つかっても運用先へ戻さない。

## タスク：同じページで検討から確認まで進める

タスクは論点の整理、決定、実装、テストを一つのページで継続する。考えるためにメモへ戻す、決まったから別のタスクへ移す、といった昇格や移動を強制しない。独立して進められる成果がある場合だけ分割する。ファイルやメソッドごとの細分化は避ける。

タイトルと本文以外に必須項目を設けない。状態・Relation・分類などの空欄を作業開始の妨げにしない。本文テンプレートは次を使い、全欄の記入を強制しない。

```markdown
## 目的

## 完了条件

## 次にやること

## 論点・決めたこと

## 作業メモ・確認結果
```

「論点・決めたこと」では未決定と採用済みを区別する。「作業メモ・確認結果」には実際に確認した内容を記載し、未実行のテストを成功扱いしない。本文全体や会話履歴を他のDBへ複製せず、継続参照が必要な要件・仕様・判断理由だけ資料へ反映し、リンクで辿れるようにする。

状態は次の6つを使い、Statusの3グループに分ける。

| グループ | 状態 | 意味 |
| --- | --- | --- |
| 未着手 | 未整理 | 内容や次にやることをまだ整理していない |
| 未着手 | 着手可能 | 次にやることが分かり、開始できる |
| 進行中 | 作業中 | 検討・実装・確認を進めている |
| 進行中 | 保留 | 他のタスクや判断を待つ、または今は進めない。本文に再開条件を残す |
| 終了 | 完了 | そのタスクの完了条件を満たした |
| 終了 | 対応不要 | 対応しないと決めた、または別のタスクへ統合した |

未整理・着手可能・対応不要は灰、作業中は青、保留はオレンジ、完了は緑にする。旧「待ち」は「保留」、旧「統合済み」は「対応不要」にまとめ、統合先と元ページの本文を残す。

検討中だから別の状態を増やしたり、資料作成だけを根拠に実装のタスクを完了にしたりしない。

Relationは必要な探索経路に絞る。

- `関連マイルストーン`、`関連要件`、`関連仕様`、`関連判断記録`を必要に応じて使う。
- 旧`起票元`は`関連メモ`へ改名し、元メモとの関係を保持する。
- `依存タスク`を使う。現在のタスクが着手・完了するために先行するタスクを指す。
- `統合先`はタスクDBへのSelf Relationとし、統合元から引き継ぐタスクを指す。
- 改名では既存Relationを維持し、同じ役割のPropertyを重複作成しない。本文のID一覧でRelationを二重管理しない。

## メモ：入力と参照を残す

運用する分類は`扱い`の`未整理`、`参照用`、`タスクへ反映済み`、`保留`とする。`扱い`が空欄のメモも未整理として扱い、受信箱の対象に含める。名前だけで追加できる経路を保ち、内容や結論を推測して分類しない。

旧`用途`・`整理先`・`状態`は履歴として保持し、通常の表示から隠して新運用には使わない。旧本文ボタンは履歴として残す。プロパティの`タスク起票`・`判断記録を作る`は設定を更新し、操作用に表示する。旧値を自動的に新分類へ読み替えて結論を確定しない。

- 考えるだけなら既存のメモでもタスクでも続けられる。タスクや資料への昇格、ページ移動を要求しない。
- 作業として追跡する必要があれば既存のタスクへ反映し、なければ必要なタスクを作る。元メモを残し、`関連メモ`で結ぶ。
- `タスクへ反映済み`はタスクへの反映を確認してから設定する。タスクの完了を意味しない。
- 参考情報は`参照用`として残せる。正式資料へ整理した場合も元メモを保持し、本文リンクなどで出典へ辿れるようにする。

## メモ・タスク・判断記録の関連と操作

- タスクの`関連メモ`とメモの`関連タスク`、タスクの`関連判断記録`と判断記録の`関連タスク`、メモの`関連判断記録`と判断記録の`関連メモ`は双方向Relationとする。
- メモの`タスク起票`はタスクのテンプレートを使い、名前・元メモ・関連マイルストーン・関連判断記録を引き継ぐ。本文の論点は人またはAIが確認して追記する。既存タスクがある場合は重複起票しない。
- メモの`判断記録を作る`は名前・記録日・元メモ・既存の関連タスクを設定し、判断記録のテンプレートを開く。決定内容と理由を記入し、採用済みと確認してから状態を`有効`にする。
- 起票後に既存の判断記録をメモへ追加した場合は、タスク側にも必要な関連を設定する。常時の自動同期と説明しない。
- プロパティはタイトル直下で基本・関連・管理に分け、必要な関連項目は空欄でも設定できるようにする。一覧は名前・状態・優先度を中心に絞る。

## タスクの統合

1. 統合先と統合元の本文・Relation、および統合元を`依存タスク`として参照するタスクを確認する。
2. 未解決論点、完了条件、決定、確認結果を重複を避けて統合先へ引き継ぐ。競合する決定を推測で解消しない。`関連メモ`など必要な参照も保持する。
3. 統合元のタスクは削除・移動せず、状態を`対応不要`、`統合先`を引き継ぎ先にする。元のメモも残す。
4. 統合元に依存するタスクの`依存タスク`を統合先へ付け替える。統合先自身が統合元に依存していた場合はその参照を除き、自分自身への依存を作らない。統合元の先行依存を引き継ぐ際も統合先自身や統合対象への不要な参照を除き、重複・循環を確認する。
5. 統合元から統合先へ辿れ、依存するタスクに古い参照だけが残っていないことを再取得して確認する。

## 要件・仕様・判断記録

- 要件は利用者が認識できる機能・目的・利用上のルールを扱う。PHPクラス、HTTP Status、DBカラムなどの技術詳細は仕様へ置く。
- 仕様は採用した振る舞いと構造を扱う。未決定の応答形式やエラーを埋め合わせて確定しない。
- 判断記録は、ユーザーが代替案とトレードオフを踏まえて選んだ、継続参照するPetDiary固有の方針と理由を扱う。比較だけのメモ、実装順、一時的な進捗から自動生成しない。
- 各DBの状態は`有効`、`置き換え済み`、`廃止`を使う。`有効`は採用済み資料としての有効性を示し、実装済みを意味しない。未決定案を有効な仕様や判断にせず、タスクやメモで扱う。
- DBの自動IDを正本にし、接頭辞は要件=`REQ`、仕様=`SPEC`、判断記録=`ADR`とする。手動の連番や`DL-YYYY-MM-DD-XX`を作らない。
- 置き換えた資料は残し、置き換え先へ辿れるようにする。状態変更は根拠のある採用・廃止に基づける。

HTTPエンドポイントは仕様DBの`HTTP・API`として扱い、`Method`・`Path`を保持する。API専用DBや「APIエンドポイント」DBを新設・運用しない。文書ID・名前・Method・Pathで既存仕様を確認し、Request・Response・エラーなどは該当仕様へ記載する。未決定項目は未決定と明記し、推測した契約を採用扱いにしない。

## 正本と根拠

| 情報 | 正本・確認先 |
| --- | --- |
| コード、テスト、DDL、migration、実行設定、AGENTS.md、Skills | Gitとローカルの実ファイル・差分 |
| 進捗、タスク、マイルストーン、採用した要件・仕様・判断、メモ | Notion |
| 他の開発でも使えるPHP・DDD・PDO・テストなどの学習 | Obsidianの既存`knowledge/pet-diary/learning` |

AIが「採用した」と書いたことは採用の証拠にならない。ユーザーの明示的な決定や、根拠を確認できる既存記録を確認する。コードだけから採用理由を創作しない。

実装事実と採用済み・未実装の方針を分ける。実装については関連コード・テスト・DDL・git diffを確認し、コミット済みかローカル変更か、テストを実行したかを区別する。コードと採用方針が食い違う場合も片方を自動で正しいことにせず、差異と必要なタスクを示す。

NotionへコードやDDL全文をコピーしない。実装参照は`GitHub参照`Propertyまたは必要な本文リンクを使う。`blob/main/...`や`tree/main/...`はその内容がmainに存在する場合だけ使い、判断時点の証拠は必要に応じてcommit固定URLにする。未コミット変更をGitHub上の証拠として示さない。

## 表示名と操作案内

「タスク」「次にやること」「進捗」を使う。ユーザーが使っている名称を、比喩や独自の呼び名に置き換えない。操作案内では、開くページと本文の見出しを区別し、実際の画面と対応させる。

## トップとビュー

トップは追加ボタン、`資料`、`今の目標`、`現在のタスク`、`受信箱`、`管理・履歴`の順に置く。資料には要件・仕様・判断記録へのリンクと、有効な資料を更新日時の降順で表示する切り替えビューを置く。

- 今の目標：現在のマイルストーンと到達点。
- 現在のタスク：`未完了すべて`はマイルストーンで絞らず、未整理・着手可能・作業中・保留をStatusのグループで表示する。`作業中`・`保留`のタブも用意する。
- 受信箱：タスクの`状態`が未整理のビューと、メモの`扱い`が未整理または空欄のビュー。マイルストーンに未所属でも表示する。
- 資料：要件・仕様・判断記録への共通ページ。有効な資料を日常の参照対象にする。
- 管理・履歴：全件、完了・対応不要、置き換え済み・廃止資料、過去のマイルストーンやアーカイブへ辿るページ。

マイルストーンを切り替えるときは目標とタスクの関連付けを更新する。`未完了すべて`は目標で絞らない。個別に目標で絞るビューがあれば、そのフィルターも確認する。Relationを書き換えるだけでビューも追従したとみなさない。表示Propertyは必要な少数に絞り、IDや旧項目は詳細・履歴に保持する。

進捗はタスクの件数で機械的に算出せず、HTTP契約の確定、層間接続、縦断検証など大きな境界を越えたときに概算更新する。ピン止めがある場合は現在よく参照する資料に限り、マイルストーン切り替え時に見直す。

## 確認・更新の進め方

1. 依頼の対象と書き込み許可を確認する。Notion MCPで必要なトップ・対象DBのschema・ページ・Relation先・ビューを読む。実際の名称や型が異なる場合は差分を確認し、通常の保存依頼を全面移行の許可と解釈しない。
2. 実装事実に関わる場合はAGENTS.mdと関連コード・テスト・DDL・ローカル差分を照合する。既存ページの更新で足りれば新規作成しない。
3. 許可された整理を行い、未決定事項は論点として残す。資料のRelationは実schemaに合わせ、別DB間の関係を一律のSelf Relationとして扱わない。
4. MCPで扱えない表示設定に限り、許可されたアプリ内ブラウザを使う。デスクトップのNotionアプリを操作するComputer Useは使わない。アプリのタグが付いていても操作許可と解釈しない。接続不可・権限不足なら該当更新を止め、未実施事項を報告する。ObsidianへPetDiary固有情報を代替保存しない。
5. 更新したページ・schema・Relation・ビューを必要に応じて再取得する。UI設定は再表示して確認する。変更内容、根拠、確認結果、未実施事項を報告する。

会話から学習内容とPetDiary固有情報を保存先へ振り分ける場合は、隣接する`../capture-learning/SKILL.md`を参照する。通常のタスク更新すべてに学習整理を追加しない。
